Binary search tree: design

Two trees, two ownership models, and the walks that tell them apart.

The parts

BT-D1BinarySearchTree owns the nodes and the answers

  • Nodes are owned through unique_ptr, so the tree's shape and the memory management are the same picture.
  • Insert and remove work through the owning slot, remove handling the classic three cases with the inorder successor.
  • Search returns the path and the step count instead of a bare yes or no, which is what lets the menu tell the O(log N) story.

BT-D2Six walks: three orders, two styles

  • The recursive versions are the three-line textbook functions.
  • The iterative ones spell out what the call stack was doing: preorder stacks subtrees still owed a visit, inorder slides down left edges and remembers the way back, postorder runs a mirrored preorder and reverses it.

BT-D3Balance is binary search as a shape

  • An inorder walk hands over the values already sorted.
  • The rebuild puts the middle of every range at the root of every subtree, halving the range at each level.

BT-D4ThreadedTree stands alone

  • Its node spends the null right pointer on a flagged link to the inorder successor.
  • Insert keeps the threads true: a new left child threads to its parent, a new right child inherits the parent's old thread.
  • The walk is two moves, slide to the leftmost node and hop to the successor, repeated until the last thread marks the end.

The decisions

BT-D6Decision: two ownership models on purpose

  • The main tree owns children as unique_ptr; the threaded tree manages its nodes by hand.
  • A thread is a non-owning link, and an owning pointer type cannot say so; forcing one model onto both trees would misdescribe one of them.

Requirements BT-R7 Tests BT-T6

BT-D7Decision: the snapshot is fed in preorder

  • The threaded tree is built from the main tree's preorder sequence, which reproduces its exact shape.
  • Feeding the inorder sequence instead would rebuild the sorted-input stick, the very shape the demo warns about.
