The parts

EL-D1BoxOffice owns the seats and the loop

  • Seat counts are private members of one object that lives on its own thread.
  • One slot applies one request, so the office's loop is the only visitor to that data.

EL-D2The queue is the mutual exclusion

  • Requests are posted, not called, so the loop serialises every access for free.
  • Arrival order becomes service order, which is where first come, first served comes from.
  • Lock ordering, contention and torn reads never arise, because there is nothing to lock.

EL-D3Every request carries a return address

  • A request holds the outlet that sent it, so the confirmation goes back to that one outlet.
  • No broadcast to all ten, and no shared result slot to guard.

EL-D4BookingAgent keeps its own books

  • Each outlet paces its own requests and keeps its own tally.
  • It times its own round trip, because the thread that stamps the send is the one that sees the reply.
  • So neither a clock nor a counter is ever shared between threads.

EL-D5StadiumView paints into a cached image

  • One pixel per seat with a one-pixel gap, drawn into a QImage that is kept between frames.
  • The image is blitted with nearest-neighbour scaling, so single seats stay crisp.

EL-D6The view is fed on a heartbeat

  • Sold seats are batched onto a 33 ms tick and sent as contiguous runs, two integers each.
  • A signal per booking would bury the GUI loop, which is the mistake this demo argues against.

EL-D7MainWindow mediates, main parses the flags

  • The window is the only class that knows the office, the outlets and the views, and the only one that starts threads.
  • The two automation flags are handled at startup, next to the metatype registration.

The decisions

EL-D8Decision: the office stops first

  • Requests hold return addresses, so the outlets must outlive the office.
  • Stop the outlets first and the office keeps replying to deleted objects.
  • The first version did exactly that and crashed on exit, which is why the order is now fixed and commented.
