Window tree: design

One class owns the tree and its walks; everything else decides one node.

The parts

WT-D1Widget owns the tree and every walk

  • The base class holds the parent and child links and every recursive pass: measure, arrange, paint, the close veto, the click dispatch, the outline and the search.
  • A derived widget only decides how its one node measures, looks and reacts; the traversals are inherited.

WT-D2Window is where actions land

  • The buttons only announce what happened; the window owns what save, reset and close actually mean.
  • An action it does not know, like help, falls through and keeps bubbling.
  • Close runs the loud veto walk and flips the flag the main loop watches.

WT-D3TextBox holds the only thing worth saving

  • A dirty flag set by typing, shown as a star on the box, cleared by the bubbled save.
  • Reset restores the default text, and that itself counts as an edit until the next save.

Requirements WT-R6 Tests WT-T4 Code TextBox.cpp

WT-D4Button and Panel stay small

  • A button is its label and the one action it raises; brackets while clickable, parentheses while disabled.
  • A panel is a titled frame that stacks whatever it is given.

WT-D5Screen knows nothing about widgets

  • A character grid with clipping, frames, and the coordinate rulers clicks are aimed with.
  • Widgets paint onto it; it never looks back at them.

WT-D6main keeps only the menu

  • The fixed demo tree, one small handler per item, and the guards: a hidden widget cannot be clicked, the window itself cannot be hidden, junk input is answered rather than crashed.

The decisions

WT-D7Decision: no inorder pass

  • Inorder means left, node, right, so it needs a binary tree, and a window tree gives a container as many children as it has widgets.
  • Leaving it out is more honest than forcing it in, and the README says so in one line.
