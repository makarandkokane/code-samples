The model and the views

OM-R1One source of truth

  • The item data lives in exactly one object.
  • No view keeps its own copy of the data.

Design OM-D1 Tests OM-T1 OM-T4

OM-R2Three views of the same data

  • An editable table, a bar chart, and a one-line summary.
  • All three agree at all times, with no refresh button anywhere.

Design OM-D2 OM-D3 OM-D4 Tests OM-T1 OM-T4

OM-R3The views do not know each other

  • No view holds a pointer, a reference or a signal connection to another view.
  • A reader can check it: search each hand-written view for the other's class name.

Design OM-D5 OM-D9 Tests OM-T6

OM-R4An edit anywhere shows up everywhere

  • Typing a value in the table moves the matching bar and updates the summary.
  • The value column stays typable, so the edit path is real and not simulated.

Design OM-D1 OM-D6 Tests OM-T1

OM-R5Rows can come and go

  • Adding a row makes it appear in all three views.
  • Removing a row makes it disappear from all three.

Design OM-D1 OM-D2 Tests OM-T2 OM-T3

When the subject goes away

OM-R6A subject that is gone says so

  • The model being destroyed is a state change, so the views observe it like any other.
  • Each hand-written view clears its pointer and prints that the subject is gone.
  • An empty model and a destroyed model must not look the same on screen.

Design OM-D2 OM-D3 OM-D8 Tests OM-T5

Automation

OM-R7The demo can capture itself

  • A command-line flag captures the window to a PNG and exits.
  • That is how the README image is produced, so it never goes stale by hand.
