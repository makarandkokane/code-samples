What the box office has to do, and the one claim the whole demo rests on.

Selling tickets

EL-R1Ten outlets sell at the same time

  • Ten outlets, each on its own thread, send requests as fast as their profile allows.
  • Twelve threads run in total once the office and the window are counted.

Design EL-D1 EL-D4 Tests EL-T1 EL-T3

EL-R2One owner of the seating plan

  • 100,000 seats in eight blocks belong to a single object.
  • Exactly one thread ever touches those counts.

Design EL-D1 EL-D2 Tests EL-T1

EL-R3First come, first served

  • Requests are served in the order they arrive.
  • Ordering must fall out of the design, not out of code written to enforce it.

Design EL-D2 Tests EL-T1 EL-T2

EL-R4The outlets are not clones

  • Party sizes and rates differ per outlet, from single seats to blocks of hundreds.
  • Some outlets insist on their own block, so a reader can watch those blocks take their own traffic while the general flood fills the bowl from the first block outward.
  • Each outlet reports its own counts and its own round trip.

The claim

EL-R5No locks anywhere

  • No mutex, no lock and no atomic in the demo code.
  • The claim has to survive a search, so it must stay true as the code grows.

Design EL-D1 EL-D2 Tests EL-T7

The window

EL-R6Every seat is visible

  • The bowl paints one pixel per seat, so a single sold seat can be seen.
  • Each block label carries its own occupancy.

Design EL-D5 Tests EL-T4

EL-R7The window stays alive under load

  • The window repaints and accepts clicks while the ground is selling out.
  • That has to hold during a burst, when the queue is deliberately overfed.

Design EL-D6 Tests EL-T4 EL-T5

Lifecycle

EL-R8Quitting mid-sale is not a crash

  • Closing the window while requests are in flight shuts everything down cleanly.

Design EL-D8 Tests EL-T6

EL-R9Two flags for unattended runs

  • --benchmark sells out at full speed and stops on the last seat.
  • --screenshot captures the window, and combines with the benchmark.
