Requirements Design Tests Code

Behaviour

EL-T1Every seat is sold exactly once

  • Run with --benchmark and let it stop on the last seat.
  • Pass: sold seats total 100,000, and the selling stops on its own, with the window still open.

Requirements EL-R1 EL-R2 EL-R3 Design EL-D1 EL-D2

EL-T2Service order follows arrival order

  • Watch the office's handled count against the sum of the outlets' sent counts.
  • Pass: the two track each other with only an in-flight lag, so nothing is dropped.
  • Ordering itself follows from the single queued slot by construction, which is the point: it is not something this run could disprove.

Requirements EL-R3 Design EL-D2

EL-T3The outlet profiles are visible

  • Let a run proceed at the default pace and read the block occupancy labels.
  • Pass: the blocks the flood has not reached yet fill only from the outlets that insist on them, and party sizes differ per outlet.

Requirements EL-R1 EL-R4 Design EL-D3 EL-D4

EL-T4The window survives a burst

  • Press Burst so the outlets stop throttling, then keep clicking and resizing.
  • Pass: the bowl keeps repainting and the controls keep responding while the ground sells out.

Requirements EL-R6 EL-R7 Design EL-D5 EL-D6

EL-T5Round trips behave like a queue

  • Read the per-outlet round-trip time at the default pace, then during a burst.
  • Pass: single-figure milliseconds at the default pace, and a clear climb under the flood.

Requirements EL-R4 EL-R7 Design EL-D4

EL-T6Closing mid-sale exits cleanly

  • Close the window while requests are in flight.
  • Pass: the process exits with no crash and no late reply to a deleted outlet.

Static check

EL-T7The no-locks claim survives a search

  • Search the demo sources for QMutex, QSemaphore, std::mutex, std::atomic and lock_guard.
  • Pass: no hits. This is the test a reader can run without building anything.
  • The words mutex and lock do appear twice, in the comment and the window title that state the claim.
